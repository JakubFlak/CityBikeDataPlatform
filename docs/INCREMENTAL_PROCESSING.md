# Incremental Processing

The local pipeline remains a library-and-script pipeline. It does not add an
orchestration framework, database, or cloud state store.

## Snapshot identity

A Raw snapshot identity is:

```text
feed_name + "|" + observed_at
```

`observed_at` is generated by this application at retrieval time, normalized to
UTC, and is already the Raw directory identity:

```text
data/raw/<feed_name>/observed_at=<timestamp>/snapshot.parquet
```

Gold may also contain `observed_at_local`, which is the same instant converted
with the IANA `Europe/Warsaw` timezone. It is presentation and calendar data
only; incremental identities, natural keys, temporal joins, and latest-snapshot
logic continue to use canonical UTC `observed_at`.

The Raw `data_json` payload is hashed with SHA-256 and stored in the control
file alongside the identity. Re-encountering the same identity with the same
hash is an idempotent duplicate. Re-encountering it with a different hash
fails rather than silently changing history. `source_url` is retained in the
control entry for lineage and diagnostics, but is not part of the primary key;
the same feed and observation time represent one source state.

## State and watermark

Silver uses a lightweight JSON control file at:

```text
data/silver/_incremental_state.json
```

It is a processed-snapshot manifest, not a time-only watermark. This avoids
missing late-arriving snapshots and supports multiple feeds with independent
collection times. A raw file is pending when its identity is absent from the
manifest or its status is not `complete`. Silver-stage entries use
`silver_complete` until downstream Gold processing succeeds. Existing Silver
rows are also deduplicated by their declared natural
keys, so the process remains safe if the state file is lost and snapshots are
replayed.

## Silver strategy

`incremental_raw_to_silver` scans Raw file metadata, parses only pending Raw
snapshots, and merges their records with existing Silver rows by table grain:

- entity + `observed_at` for canonical entities
- station + vehicle type + `observed_at` for vehicle availability
- plan + tier + `observed_at` for pricing tiers

All tables are staged in a temporary directory and atomically replaced only
after every table has been successfully materialized. The manifest is written
last. Therefore a failure before commit leaves the previous Silver state and
causes the pending snapshots to be retried on the next run.

The current local format is one Parquet file per table, so committing a batch
rewrites those table files. The expensive JSON-to-record transformation is
limited to new snapshots. Partitioned output can be introduced later if file
rewrite cost becomes material at larger scale.

## Gold strategy

`incremental_silver_to_gold` creates a complete candidate Gold result from all
current Silver tables. It validates every candidate schema and atomically
replaces the existing Gold output through the same staged Parquet commit used
by Silver. It does not merge with or compare against the previous Gold output,
so an older artifact can migrate to a new Gold schema without manual cleanup.
Temporal joins still use the existing nearest-feed match within the bounded
five-minute tolerance; a match outside the tolerance or an ambiguous/conflicting
key fails.

Because the current derived table is a small, non-partitioned aggregate,
`gold_system_availability` is recomputed from the complete fact set. This is
deliberately simple and correct. Station history metrics are not materialized;
they are calculated from `fact_station_availability` in the selected report
context. A future partitioned format can update only affected timestamps once
scale justifies the additional state and validation.

Gold output is staged and atomically replaced. A failed candidate build or
schema validation leaves the previous Gold output unchanged.

## Running the incremental pipeline

```text
python scripts/transform_incremental.py
```

The command is safe to run repeatedly. With Raw snapshots A, B, and C it
produces A, B, and C. After D and E arrive, the next run processes D and E and
retains A, B, and C. Running it again produces no additional rows.

## Guarantees and limitations

- deterministic sorting and key-based deduplication
- idempotent replay of identical Raw snapshots
- conflicting same-identity payloads fail explicitly
- restart after a failed Silver or Gold build is safe
- temporal dimension state is not replaced by a latest-only join
- single-file Parquet commits currently rewrite output files even though only
  new Raw payloads are parsed into Silver
- the control manifest is local operational state and should be backed up with
  the pipeline outputs if recovery across machines is required
